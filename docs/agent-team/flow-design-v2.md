# 开发流程设计 v2（含调研层与文档维护）

> 2026-11-20 重设计。核心改动：**先调研、后写文档**，因为 AI 写文档质量差的根因不是「不会写」，
> 而是「没读代码就写」。

## 一、为什么 v1 失败

实跑三次的结论：

| 现象 | 真因 |
|---|---|
| 需求文档写成「实现完成报告」 | 节点没有区分「写文档」和「做实现」的边界，agent 拿到需求就想动手 |
| 审计两次 FAIL | 审计没错，是上游产物类型错了 |
| 文档内容空泛、断言不实 | **AI 从没读过现有代码**，全靠想象 |

**关键洞察**：审计能发现问题，但只有上游「有事实可依」时才有意义。
现在缺的不是审计层，是**事实层**。

## 二、新流程：11 个节点

```
┌─────────────┐
│ 1 代码调研   │  ← 新增，产出事实清单（F1/F2/F3…）
└──────┬──────┘
       ↓
┌─────────────┐     ┌──────────────┐
│ 2 需求文档   │────→│ 3 需求审计    │──FAIL(≤2)──┐
└─────────────┘     └──────┬───────┘            │
       ↑                   │PASS                 │
       └───────────────────┼─────────────────────┘
                           ↓  ★ 人工确认
                    ┌─────────────┐     ┌──────────────┐
                    │ 4 设计文档   │────→│ 5 设计审计    │──FAIL(≤2)──┐
                    └─────────────┘     └──────┬───────┘            │
                           ↑                   │PASS                │
                           └───────────────────┼────────────────────┘
                                               ↓  ★ 人工确认
                                        ┌─────────────┐
                                        │ 6 技术方案   │
                                        └──────┬──────┘
                                               ↓
                                        ┌─────────────┐
                                        │ 7 编码实现   │◄─────┐
                                        └──────┬──────┘      │
                                               ↓             │FAIL(≤3)
                                        ┌─────────────┐      │
                                        │ 8 代码审查   │──────┘
                                        └──────┬──────┘  ★ 人工审批
                                               ↓ PASS
                                        ┌─────────────┐
                                        │ 9 测试验证   │
                                        └──────┬──────┘
                                               ↓
                                        ┌─────────────┐
                                        │ 10 文档维护  │  ← 新增
                                        └─────────────┘
```

## 三、每个节点的职责

| # | 节点 | agent | 做什么 | 产物 | 人工 |
|---|---|---|---|---|---|
| 1 | **代码调研** | ekko-agent | 用只读工具真实检索代码：有哪些相关文件、现有实现长什么样、依赖了什么、有没有类似功能 | **事实清单 F1…Fn**（每条带文件路径 + 行号 + 摘录） | — |
| 2 | 需求文档 | ekko-agent | 基于事实清单写需求，**每条断言必须挂 F 编号** | 目标/范围/验收，每条带 `[F2]` 引用 | **确认** |
| 3 | 需求审计 | ekko-agent | 查：有没有引用不存在的 F、有没有没挂 F 的断言、验收是否可判定 | PASS/FAIL | — |
| 4 | 设计文档 | ekko-agent | 基于事实 + 需求写设计，同样挂 F | 流程/数据/边界，每条带 F | **确认** |
| 5 | 设计审计 | ekko-agent | 查：设计是否每条需求都覆盖、数据结构能否支撑、F 引用是否成立 | PASS/FAIL | — |
| 6 | 技术方案 | ekko-agent | 文件级改动计划（新增/修改/删除），引用 F 说明现状 | 文件树 + 实施顺序 | — |
| 7 | 编码实现 | opencode | 按方案改代码（**唯一允许写文件的节点**） | 改动清单 + 验证结果 | — |
| 8 | 代码审查 | ekko-agent | 只读审查，PASS/FAIL | 问题清单 | **审批** |
| 9 | 测试验证 | opencode | 跑真实测试 | 验收对照 + 缺陷 | — |
| 10 | **文档维护** | ekko-agent | 更新 CHANGELOG、docs 索引、接口文档、fleet-roster 类清单 | 文档改动清单 | — |

## 四、质量控制的三道锁

### 锁 1：事实清单（解决「调查不彻底」）

调研节点的硬要求：

```
每条事实必须是一行：
F1 | packages/server/src/modules/studio/routes/workflows.ts:23 | 已有 POST /:id/run 路由
```

后续所有文档**只能引用 F 编号**，审计专门抓「引用了不存在的 F」。

这一条把「AI 编造」从"事后发现"变成"结构性不可能"。

### 锁 2：文档节点禁写代码

文档类节点（1-6、8、10）的 prompt 末尾统一挂：

```
【硬约束】
本节点只产出 Markdown 文档。禁止使用任何写文件、执行命令、修改仓库的工具。
如果你发现自己想改代码，说明你误解了任务：把想改的地方写成「建议改动」列在文档里。
```

注意：**只在 prompt 里写不够**（v1 证明过）。真正的隔离靠分工——
文档节点用 `ekko-agent`，编码/测试用 `opencode`（cwd 受限）。

### 锁 3：人工确认点

| 位置 | 类型 | 含义 |
|---|---|---|
| 需求文档后 | approvalRequired | 需求定稿，人可以改 |
| 设计文档后 | approvalRequired | 设计定稿 |
| 代码审查后 | approvalRequired | 代码合并前最后一道 |

用户原话：「需求和设计阶段本来就是最后同意了，就要有一次跟人的交互」。
所以这两个位置**必须有**停顿，不是可选项。

## 五、为什么不建群

| 路线 | 上下文成本 | 隔离性 |
|---|---|---|
| 群聊 | 全房间历史累积给每个 agent | 差 |
| **workflow** | 每节点独立 session，只吃上游产物 | 好 |

workflow 节点是 `WorkflowRunNodeSessionRecord`，上下文天然隔离。

## 六、已知限制

| 限制 | 说明 |
|---|---|
| ekko-agent 有全局文件工具 | workspace 隔离对它无效，它能读写任意绝对路径。锁 2 只能靠 prompt + 人工兜底 |
| claude-code / codex 不能用商汤 | 协议不匹配（anthropic_messages / codex_responses vs chat_completions） |
| 流程长 | 10 个节点串行，全跑完 20-40 分钟。可以中途停，已完成的节点产物保留 |
| 商汤限流 | 4010 RPM 低，节点间可能 429，脚本要带重试 |

## 七、适用规模

| 需求规模 | 建议 |
|---|---|
| 一行改动 | 别用，直接单聊 |
| 一个功能点（半天） | 用节点 1-6，跳过审计 |
| 一个模块（几天） | 全流程 |
| 跨模块重构 | 全流程 + 每个阶段都人工确认 |
