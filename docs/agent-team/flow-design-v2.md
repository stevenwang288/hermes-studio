# 开发流程设计 v2（含调研层与文档维护）

> 2026-11-20 重设计。核心改动：**先调研、后写文档**，因为 AI 写文档质量差的根因不是「不会写」，
> 而是「没读代码就写」。

## 一、为什么 v1 失败

实跑三次的结论：

| 现象 | 真因 |
|---|---|
| 需求文档写成「实现完成报告」 | 节点没有区分「写文档」和「做实现」的边界，agent 拿到需求就想动手 |
| 审计两次 FAIL | 审计没错，是上游产物类型错了 |
| 文档内容空泛、断言不实 | **AI 从没读过现有代码**，全靠想象 |

**关键洞察**：审计能发现问题，但只有上游「有事实可依」时才有意义。
现在缺的不是审计层，是**事实层**。

## 二、新流程：11 个节点

```
┌─────────────┐
│ 1 代码调研   │  ← 新增，产出事实清单（F1/F2/F3…）
└──────┬──────┘
       ↓
┌─────────────┐     ┌──────────────┐
│ 2 需求文档   │────→│ 3 需求审计    │──FAIL(≤2)──┐
└─────────────┘     └──────┬───────┘            │
       ↑                   │PASS                 │
       └───────────────────┼─────────────────────┘
                           ↓  
                    ┌─────────────┐     ┌──────────────┐
                    │ 4 设计文档   │────→│ 5 设计审计    │──FAIL(≤2)──┐
                    └─────────────┘     └──────┬───────┘            │
                           ↑                   │PASS                │
                           └───────────────────┼────────────────────┘
                                               ↓  
                                        ┌─────────────┐
                                        │ 6 技术方案   │
                                        └──────┬──────┘
                                               ↓
                                        ┌─────────────┐
                                        │ 7 编码实现   │◄─────┐
                                        └──────┬──────┘      │
                                               ↓             │FAIL(≤3)
                                        ┌─────────────┐      │
                                        │ 8 代码审查   │──────┘
                                        └──────┬──────┘  
                                               ↓ PASS
                                        ┌─────────────┐
                                        │ 9 测试验证   │
                                        └──────┬──────┘
                                               ↓
                                        ┌─────────────┐
                                        │ 10 文档维护  │  ← 新增
                                        └─────────────┘
```

## 三、每个节点的职责

| # | 节点 | agent | 模型 | 做什么 | 产物 |
|---|---|---|---|---|---|
| 0 | **代码调研** | ekko-agent | 商汤 deepseek-flash | 用只读工具真实检索代码：涉及哪些文件、现有实现、依赖、有无类似功能 | **事实清单 F1…Fn**（路径 + 行号 + 摘录） |
| 1 | 需求文档 | ekko-agent | 商汤 deepseek-flash | 基于事实清单写需求，**每条断言必须挂 F 编号** | 目标/范围/验收，每条带 `[F2]` |
| 2 | 需求审计 | ekko-agent | **腾讯 deepseek-v4-pro** | 查：悬空 F 引用、无依据断言、验收可判定性 | PASS/FAIL + 悬空 F 清单 |
| 3 | 设计文档 | ekko-agent | 商汤 deepseek-flash | 基于事实 + 需求写设计，同样挂 F | 流程/数据/边界，每条带 F |
| 4 | 设计审计 | ekko-agent | **腾讯 deepseek-v4-pro** | 查：需求覆盖、F 引用成立性、数据结构支撑度 | PASS/FAIL + 覆盖对照 |
| 5 | 技术方案 | ekko-agent | 商汤 deepseek-flash | 文件级改动计划，引用 F 说明现状 | 文件表 + 实施顺序 + 风险 |
| 6 | 编码实现 | opencode | 商汤 deepseek-flash | 按方案改代码（**唯一允许写文件的节点**） | 改动清单 + 验证结果 |
| 7 | 代码审查 | ekko-agent | **腾讯 deepseek-v4-pro** | 只读审查，逐条对照验收标准 | PASS/FAIL + 问题清单 |
| 8 | 测试验证 | opencode | 商汤 deepseek-flash | 跑真实测试，不假设通过 | 验收对照 + 缺陷 |
| 9 | **文档维护** | ekko-agent | 商汤 deepseek-flash | 更新 UPDATE_LOG、docs 索引、公开 API 注释、清单类文档 | 文档改动清单 |

## 四、质量控制的三道锁

### 锁 1：事实清单（解决「调查不彻底」）

调研节点的硬要求：

```
每条事实必须是一行：
F1 | packages/server/src/modules/studio/routes/workflows.ts:23 | 已有 POST /:id/run 路由
```

后续所有文档**只能引用 F 编号**，审计专门抓「引用了不存在的 F」。

这一条把「AI 编造」从"事后发现"变成"结构性不可能"。

### 锁 2：文档节点禁写代码

文档类节点（0-5、7、9）的 prompt 末尾统一挂：

```
【硬约束】
本节点只产出 Markdown 文档。禁止使用任何写文件、执行命令、修改仓库的工具。
如果你发现自己想改代码，说明你误解了任务：把想改的地方写成「建议改动」列在文档里。
```

注意：**只在 prompt 里写不够**（v1 证明过）。真正的隔离靠分工——
文档节点用 `ekko-agent`，编码/测试用 `opencode`（cwd 受限）。

### 锁 3：审计独立性与严格度

**独立性**：写手用商汤 `deepseek-flash`，审计用腾讯 `deepseek-v4-pro`。
同一个模型审自己写的东西，几乎必然放行。

| 节点 | 写手模型 | 审计模型 |
|---|---|---|
| 需求 | 商汤 deepseek-flash | **腾讯 deepseek-v4-pro** |
| 设计 | 商汤 deepseek-flash | **腾讯 deepseek-v4-pro** |
| 代码 | 商汤 deepseek-flash | **腾讯 deepseek-v4-pro** |

**严格度**：每个审计节点末尾挂：

```
【审计硬要求】
- 你必须逐项输出「检查项 / 结果 / 依据」，不能只写结论
- 即使 PASS，也要列出你验过的每一条
- 如果你无法验证某一项（缺信息），写「无法验证」，并视为 FAIL 的高危项
- 严禁为了让流程通过而放宽标准。宁可 FAIL 让人重做，也不要放过问题
```

**全自动，无人工卡点**。审计 FAIL 由 feedback 边自动退回重写，
超过迭代上限（需求/设计 2 次、代码 3 次）则整个 run 停止，不会无限循环。

## 五、为什么不建群

| 路线 | 上下文成本 | 隔离性 |
|---|---|---|
| 群聊 | 全房间历史累积给每个 agent | 差 |
| **workflow** | 每节点独立 session，只吃上游产物 | 好 |

workflow 节点是 `WorkflowRunNodeSessionRecord`，上下文天然隔离。

## 六、已知限制

| 限制 | 说明 |
|---|---|
| ekko-agent 有全局文件工具 | workspace 隔离对它无效，它能读写任意绝对路径。锁 2 只能靠 prompt + 人工兜底 |
| claude-code / codex 不能用商汤 | 协议不匹配（anthropic_messages / codex_responses vs chat_completions） |
| 流程长 | 10 个节点串行，全跑完 20-40 分钟。可以中途停，已完成的节点产物保留 |
| 商汤限流 | 4010 RPM 低，节点间可能 429，脚本要带重试 |

## 七、适用规模

| 需求规模 | 建议 |
|---|---|
| 一行改动 | 别用，直接单聊 |
| 一个功能点（半天） | 用节点 1-6，跳过审计 |
| 一个模块（几天） | 全流程 |
| 跨模块重构 | 全流程，每阶段跑完后人工看一眼产物再继续 |
